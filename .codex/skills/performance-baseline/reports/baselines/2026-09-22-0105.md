# 2026-09-22 冷启动分段基线：`perf/instant-nav` 启动埋点首轮

## 本轮要回答的问题

冷启动 ~650-760ms 到底花在哪：rAF 150ms 兜底嫌疑是否存在、前端 slice 占比多少、native 地板在哪。前提：`perf/instant-nav`（自 `perf/startup-bundle-split` HEAD 切出）新埋点首发——`native_ready` / `setup_end` 升 Info、新增 `page_load_finished`（Rust 时钟）与 `state_ready` / `window_pre_show` / `window_shown`（前端上报，折算同一进程起点时钟）。全部折算到 `StartupClock`，一条时间线可对齐。

## 用户可感知指标

### 冷启动（App 全关 → 主窗口可见）

探针 20 轮：**稳态中位 758 ms（区间 740-815）**。

**跨场次可比性警告**：与 2026-09-20 基线的 646 ms 不构成同期对照（未交错、时段不同），758 vs 646 **不下回归结论**；本轮的价值是绝对分段，不是 A/B。

### 启动分段（同一进程起点时钟，n=20 完整冷启动）

| 里程碑 | 中位 | 区间 | 含义 |
|---|---:|---|---|
| `native_ready` | **585 ms** | 569-613 | 进程 spawn + Rust init + tauri runtime + **主窗口与 WebView2 控制器冷创建**（config 窗口先于 setup 创建） |
| `setup_end` | 605 ms | 587-634 | setup 本体仅 ~20 ms（DB/插件/托盘，已够瘦） |
| `page_load_finished` | 657 ms | 642-703 | WebView 文档导航完成（+52 ms） |
| `state_ready`（frontend） | **313 ms** | 301-331 | 文档起点 → get_state 完成 + 首屏渲染就绪（JS bootstrap 全部） |
| 出窗 | ~740-815 | — | probe `Visible` 与前端时间线互洽（pre_show ≈ visible 前 ~5-50ms） |

**结构性结论：585/758 ≈ 77% 的冷启动发生在任何一行项目代码（Rust setup 或前端）执行之前**——进程 spawn + WebView2 冷创建是平台地板。托盘段的 single-instance 短命二进程（主实例存活时启动）`native_ready` 仅 ~270-300 ms，**直接证明 WebView2 池热时可省 ~300 ms**。

### 托盘恢复

20 轮全部 `HiddenBefore=True`，**恢复中位 294 ms（区间 284-321）**。该维度首次可测（此前 `minimize_to_tray: false` 不可测）。托盘恢复 294 ms 里含探针 Start-Process 新进程 + single-instance 唤醒，比纯 `show()` 偏慢；纯热显示应更快。

## 关键疑点裁决

**rAF 150ms 兜底嫌疑：排除。** `window_pre_show` detail 实测 `raf wait_ms=51`（唯一存活样本），150ms 兜底从未触发——Chromium 对隐藏 WebView2 窗口不节流 rAF（至少本机不节流）。等待成本实为 **46-77ms 的双 rAF**，是"防热重启白帧"的合理代价，可评估减半但不属"白等税"。

## 方法学发现

1. **探针杀进程竞态吃掉了 `window_shown` 埋点**：窗口可见 → 探针判 responsive → `Stop-Process`，而 show 之后的上报（+50ms）来不及落盘，20 轮仅最慢的 1 轮存活。已修：rAF 留痕上报挪到 show 之前（`window_pre_show`），`window_shown` 保留在 show 之后补全时间线。
2. **探针 stdout 截断**：本轮 `tail -40` 只留了末尾，20 轮逐次明细未归档。下轮起探针输出应整文件落盘再分析。
3. single-instance 短命二进程也打 `native_ready`（随后在插件 init 处退出，无 setup_end）——分析时按 `native_ready > 400ms` 过滤完整启动。
