## 新代码路径确实被测到了（不是空跑）

冷启动最该担心的是「新增的 Claude 被动收割给 `get_state` 加了多少」。本轮排除了这个疑虑：

- 数据库里 `claude_profiles` 有 **5 行**，`app_state.active_claude_profile_id` = `cla-1790700312430-0`（**智谱官方**）——**存在激活的 Claude 配置**，所以 `ClaudeSyncBody` 的 `StateRefresh` 分支没有走 `NoActiveProfile` 早退，而是真的读了 `~/.claude/settings.json` 并做了比对。
- 换句话说：**本轮 534 ms 是包含新同步层开销的数字**，不是绕开新代码测出来的。
- 佐证：dev 会话日志里可见成对的 `client="Codex" reason=unchanged` + `client="Claude Code" reason=unchanged`（双引擎都在跑且都判定无变化，不写库）。
- `[sync.harvest]` 的 50ms 预算告警是 `warn!` 级（release 可见），**全日志历史 0 条**——同步层从未超预算。

**但 release 下同步层完全不可观测**：`[sync.harvest]` 的每轮结局是 `debug!`，而 release 构建按 `lib.rs` 的配置只出 Info。
所以探针那 41 次 release 启动在日志里留下 0 行 sync 记录——本轮「同步开销」的判断只能靠
「预算告警从未触发」这一条间接证据，拿不到每次的实测毫秒数。若要把同步开销变成常规可测项，
需要把每轮结局或耗时提到 `info!`（或让探针可切换日志级别）。

Defender 缓存状态或真实代码变更，无法拆分。

但有一点值得单独指出：本轮产物是**双引擎**版本（Codex + Claude Code），
理应比 09-22 的单引擎版本更重，实测却全线更快——这个反直觉方向建议
**在可控条件下做一次交错 A/B 再定性**，否则不作为结论使用。
